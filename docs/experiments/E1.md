# E1 edge-based Dijkstra throughput

E1 requires at most 150 ns per settled label and at least 5x the oracle's
label throughput for the same expansions. The native Germany run exceeded
150 ns for both kernels. The matched Valhalla measurement remains open.

## Luxembourg pilot

The search kernel was at `4ec7924`, built in ReleaseFast with
`0.17.0-dev.1857+3c46da14d`. The pilot ran in an aarch64 Linux VM with six
virtual CPUs on an Apple M3 Pro. The native bundle used the Geofabrik
Luxembourg 2026-01-01 PBF, SHA-256
`d8f3e1dabb4d9d5489500c35432eb393089c32222cfff8cf50706852f0696a80`.
The bundle contains 187,650 nodes and 475,336 directed edges.

The experiment drew ten source nodes with seed 82 and warmed each source
once per kernel. The cap was one million labels per sweep. The reported
weighted mean divides total elapsed time by total settled labels.

| Kernel | Settled labels | Largest sweep | Weighted ns/label | Median ns/label |
| --- | ---: | ---: | ---: | ---: |
| Pedestrian | 4,584,670 | 458,467 | 173.731 | 166.102 |
| Stub motor | 2,333,384 | 291,673 | 198.297 | 167.328 |

Two stub motor sweeps settled zero labels. The median uses the nonempty
sweeps. Both pilot kernels exceeded 150 ns per label. The VM exposed
software event sources, and all hardware counter fields were null. The
5x comparison awaits the matched Germany run.

## Bounded expansion

The bounded Dijkstra from [#158](https://github.com/zig-utils/zig-routing/issues/158)
uses the same runner, graph, sources, kernels and label cap as the pilot
above. A ReleaseFast build on the same aarch64 Linux VM ran five paired
trials, alternating which queue ran first. Each result is the median of
five weighted means.

| Kernel | Settled labels per trial | Heap ns/label | Bucket ns/label | Change |
| --- | ---: | ---: | ---: | ---: |
| Pedestrian | 4,584,670 | 140.335 | 139.933 | -0.29% |
| Stub motor | 2,333,384 | 110.580 | 107.424 | -2.85% |

Settled counts matched for every source. Expansion follows Valhalla's
addition order for accumulated, traversal and transition costs. The rounding
can change when a queued label is replaced, so popped counts varied by
seven entries for pedestrian and one for the motor stub. Both kernels met
the 10% budget against the paired heap and the historical Luxembourg pilot.

Use `--bucket` to measure expansion with the cost profile's compiled unit
size.

```bash
zig build bench-search -Doptimize=ReleaseFast -- BUNDLE 10 1000000 82 --bucket > expansion.json
```

## Native Germany measurement

The ReleaseFast runner at `ccbde15` used Zig `0.17.0-dev.1857+3c46da14d` on
native x86-64 Linux `7.0.0-1018-aws`, with eight AMD EPYC 9R14 vCPUs and
16 GiB RAM. The verified Germany bundle contains 23,098,100 nodes and
58,764,002 directed edges, with UUID `5824147f09d28d8f8c9cf34cf92feb6e`.
[Pinned inputs and bundle reproduction](../../oracle/README.md#germany-build-reproducibility)

The runner warmed ten fixed sources from seed 82 and capped each sweep at
one million settled labels with the heap queue. The same source IDs,
settled counts and popped counts repeated across all three trials. Each
pedestrian sweep reached the cap. Nine stub-motor sweeps reached the cap
and one settled zero labels. Hardware counters cover userspace execution.
Each table entry is the median of three per-label values, weighted within
each trial by the number of labels settled.

| Kernel | Settled labels per trial | ns/label | Cycles/label | Instructions/label | Cache misses/label | Branch misses/label |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Pedestrian | 10,000,000 | 252.181 | 921.86 | 1,975.55 | 3.369 | 10.970 |
| Stub motor | 9,000,000 | 238.141 | 869.95 | 1,345.24 | 6.599 | 9.957 |

Pedestrian took 1.68x the 150 ns budget and the stub motor took 1.59x.
[#265](https://github.com/zig-utils/zig-routing/issues/265) tracks the search
layout work. The 5x comparison requires the same expansions in Valhalla.

### Successor label handling

The search reuses the predecessor's dead-end result across forward successors
and grows label storage only when it reaches capacity. Five alternating
pairs used the same Germany bundle, hardware and source IDs. All settled
and popped counts matched.

| Kernel | Median base ns/label | Median updated ns/label | Median paired change |
| --- | ---: | ---: | ---: |
| Pedestrian | 251.96 | 247.43 | -1.95% |
| Stub motor | 238.00 | 229.10 | -3.49% |

## Reproduction

```bash
zig build bench-search -Doptimize=ReleaseFast -- BUNDLE 10 1000000 82 > result.json
```

The report records the dataset UUID, architecture, seed, source IDs, settled
and popped labels, elapsed time and per-label hardware counters. The
pedestrian kernel uses the compiled default profile with an unbounded
distance budget for Dijkstra. The motor stub uses tagged access, base speed,
the turn restriction bit and stop impact.

The Germany run should use the same graph, source nodes, cost kernels and
one-million-label cap on both engines. If E1 misses either gate, profile
loads of the hot edge and label records alongside the queue and turn tables
before changing their sizes or layout.
